Dynamic Multi-Criteria Request Routing and Load Balancing Architecture for 6G Network Slicing
1. Architectural Foundation and Operational Workflow
The transition toward sixth-generation (6G) cellular networks represents a fundamental evolution from network-centric connectivity to hyper-automated, service-oriented virtualized environments1. Central to this architecture is end-to-end (E2E) network slicing, which partitions a common physical substrate consisting of radio access networks (RAN), transport backhaul, and multi-access edge computing (MEC) nodes into dedicated logical networks1. Each slice operates as an autonomous virtual network tailored to specific Service Level Agreements (SLAs)3.
The incoming service requests are categorized into three standardized baseline service types defined by the International Telecommunication Union (ITU-R) and 3GPP: Enhanced Mobile Broadband (eMBB), Ultra-Reliable Low-Latency Communications (URLLC), and Massive Machine-Type Communications (mMTC)6. To support heterogeneous applications—ranging from holographic telepresence to autonomous driving and industrial Internet of Things (IoT)—the load balancer cannot rely on traditional single-metric heuristics such as Round-Robin or Least-Connections8. Instead, it must execute slice-aware, multi-criteria request routing11.
1.1 End-to-End System Architecture
The architectural framework consists of five distinct functional layers that operate synchronously to route traffic based on real-time node state telemetries and slice specifications:
* Terminal and Device Layer: Represents heterogeneous end-user equipment (UE), autonomous vehicles, industrial actuators, and massive IoT sensor arrays initiating service sessions across diverse spatial locations2.
* Slice Classification Gateway: Ingests incoming packets and inspects the Single Network Slice Selection Assistance Information (S-NSSAI) header5. The S-NSSAI contains the Slice/Service Type (SST) indicator, which maps requests to eMBB (SST-1), URLLC (SST-2), or mMTC (SST-3) profiles5.
* 6G Multi-Criteria Load Balancer Engine: The core decision-making entity. It continuously ingests high-frequency telemetry metrics from available candidate processing nodes, normalizes incoming indicators, applies slice-specific priority weights, and evaluates candidate server suitability9.
* Edge Computing Layer (Candidate Nodes   ): A distributed set of Multi-access Edge Computing (MEC) nodes situated at cell sites, regional aggregation points, or central offices11. Each node possesses distinct computational, memory, caching, and database storage capacities11.
* Central Cloud and Content Delivery Network (CDN) Layer: Connects edge nodes via backhaul transport networks to core data centers, accommodating overflow traffic, heavy cloud rendering, and global content repositories14.
1.2 End-to-End Operational Execution Flow
The operational execution of a service request follows a structured multi-stage sequence:
First, a terminal device requests a session by transmitting data packets tagged with its assigned S-NSSAI identifier5. The Slice Classification Gateway intercepts the packet stream, extracts the SST parameter, and forwards the classified request to the 6G Multi-Criteria Load Balancer.
Second, the Load Balancer queries its local Telemetry Ingestion Cache, which maintains real-time metrics pulled from candidate edge nodes (   through   ) and transport network monitoring agents1. These metrics include compute utilization, queuing state, bandwidth availability, packet loss, and link latencies9.
Third, the Load Balancer executes a mathematical normalization procedure, transforming raw multi-dimensional metrics into a standardized scalar domain between zero and one. Cost parameters (where lower values are preferable, such as latency or packet loss) are converted into standardized benefit scores9.
Fourth, the Load Balancer selects a pre-configured or dynamically updated Analytic Hierarchy Process (AHP) weight vector corresponding to the request's slice type9. By multiplying the normalized metric matrix by the slice weight vector, the engine calculates a composite routing score for each candidate server10.
Fifth, the Load Balancer selects the candidate server exhibiting the maximum composite score11. If the selected edge node has the required content cached or compute capacity available, it processes the task locally and returns the output directly to the device14. If an edge cache miss occurs or computational limits are breached, the edge node orchestrates a fast backhaul fetch from the Central Cloud/CDN layer before completing the service loop14.

3. Slice-Specific Quality of Service (QoS) and KPI Requirements
The core objective of dynamic request routing is translating standardized slice specifications into specific parameter priority profiles1.
eMBB slices prioritize network bandwidth, caching capacity, memory buffer availability, and high compute performance4. These parameters ensure the network maintains sustained high-bitrate data transfers for immersive media, spatial computing, and high-definition video streams2.
URLLC slices prioritize low network latency, minimal queue lengths, high reliability, zero latency jitter, low packet loss rates, and short physical propagation distances7. These metrics ensure the load balancer selects nodes capable of fulfilling strict, deterministic timing and fault-tolerance constraints7.
mMTC slices prioritize active request capacity, composite server load, connection density, and node energy efficiency7. Throughput and latency metrics are deemphasized, enabling the load balancer to distribute lightweight IoT updates across energy-efficient edge nodes7.

5. Conclusions
This study demonstrates that request routing and load balancing within 6G network slicing architectures require a shift from conventional load-centric scheduling to dynamic multi-criteria decision models11. By parameterizing node compute profiles, database responsiveness, and network transport indicators, the proposed framework aligns routing decisions directly with slice-specific SLAs3.
Integrating mathematical normalization techniques with slice-weighted AHP-TOPSIS scoring mechanisms enables the load balancer to balance trade-offs across competing network constraints9. eMBB traffic is routed toward high-throughput, cache-enabled edge nodes; URLLC traffic is dispatched to low-latency, highly reliable processing environments; and mMTC traffic is distributed across high-capacity, energy-efficient infrastructure nodes4.
This dynamic request-routing architecture improves overall resource utilization, prevents localized edge node congestion, and preserves end-to-end slice isolation across next-generation wireless networks1.
